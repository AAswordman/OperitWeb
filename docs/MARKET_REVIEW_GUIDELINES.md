# Operit 插件市场审核规范

## 目的

人工审核只处理系统无法可靠判断的内容：项目是否真实有用、改动是否有意义、是否存在风险，以及是否有明显的幻觉或欺骗性内容。

必填字段、安装配置、资产格式和其他大多数可自动判定的问题，由发布系统负责拦截。**但市场登记版本与发行内容中的版本声明是否一致，属于审核必须确认的硬性条件，不能因为资产已被系统接收而跳过。**

审核对象是具体版本。同一项目的多个待审版本应分别处理。

## 市场简介完整性（必检）

市场简介可以简短，但必须用自己的内容说明插件实际提供的核心功能或用途。仅重复标题，或仅在标题后添加“插件”“工具”“MCP”等泛称，不构成有效简介。

发现这类简介时，必须使用 `changes` 和 `metadata-incomplete` 打回，并在 `reviewDetail` 要求作者补充可帮助用户判断是否需要安装的功能说明；涉及权限、联网、数据处理或前置条件时，也应一并写明。

## 版本登记一致性（必检）

每个待审版本都必须确认市场登记的 `version.version` 与发行内容的版本声明一致：

- `package` / `script`：与发行包内 `manifest.json` 或等价元数据中的版本一致；
- `skill` / `mcp`：若提交源、发行 tag 或内容元数据声明了版本，必须与市场登记一致；
- 不存在可核验版本声明的类型，不凭空阻拦，但不得把不一致误判为“没有声明”。

发现不一致时，必须使用 `changes` 和 `repository-content-invalid` 打回，并在 `reviewDetail` 写明市场登记版本、包内或源内实际版本，以及作者应重新打包或重新登记的目标版本。审核人不得用通过审核来掩盖版本不一致，也不得把不同版本的资产当作同一版本上架。

## 审核接口

审核接口均使用管理员或审核员的登录令牌，或审核员从审核台生成的 Agent 审核密钥：

```http
Authorization: Bearer <admin_or_reviewer_token_or_agent_key>
```

也可以使用请求头 `x-operit-admin-token`。所有接口的基础地址为 `https://api.operit.app`。Agent 密钥可以随时在审核台轮换；轮换后旧密钥立即失效，且该密钥不具备精选、下架或构建权限。

### 读取待审队列

```http
GET /market/v2/admin/review/entries?stateCode=pending&limit=50&offset=0
```

`items[]` 的每一行代表一个待审版本，而不是一个项目。以 `item.id` 作为 `entryId`，以 `item.version.id` 作为 `versionId`；同一项目有多个待审版本时必须分别审核。

### 读取项目审核详情

```http
GET /market/v2/admin/review/entries/{entryId}
```

返回项目资料、`versions[]`、仓库来源或托管资产。审核原作者更新时，用它确认是否已有通过版本及版本发布者；审核换作者更新时，用最近通过版本作为对比基线，再拉取 API 返回的仓库来源或资产进行比较。

### 提交结论

```http
POST /market/v2/entries/{entryId}/review/approve
Content-Type: application/json

{ "entryId": "{entryId}", "versionId": "{versionId}", "reviewDetail": "审核通过；未发现超出声明用途的行为。" }
```

```http
POST /market/v2/entries/{entryId}/review/changes
Content-Type: application/json

{ "entryId": "{entryId}", "versionId": "{versionId}", "reasonCode": "ai-hallucination", "reviewDetail": "声明的功能未在提交内容中实现，请补充实现或修正说明。" }
```

```http
POST /market/v2/entries/{entryId}/review/reject
Content-Type: application/json

{ "entryId": "{entryId}", "versionId": "{versionId}", "reasonCode": "security-risk", "reviewDetail": "发现与声明功能无关的数据外传逻辑，无法通过。" }
```

`entryId` 必须与 URL 一致，且 `versionId` 必须属于该项目。`changes` 与 `reject` 必须携带原因码。已上架项目审核新版本时，操作只作用于目标版本；首次发布的审核结论同时作用于项目和目标版本。

### 审核说明（`reviewDetail`）

`reviewDetail` 是附在**具体版本**上的人工说明，最长 4000 个字符，支持 Markdown。审核台在打回或拒绝时要求填写；通过时可选。它会写入私有作者条目数据和管理员审核详情，不会出现在公开市场列表或公开条目中。

说明只写实际发现的问题和作者可执行的修正方向；需要时可以注明受影响的文件、包内版本或联网行为。不要写入令牌、Cookie、用户数据、完整恶意载荷或其他敏感信息。

## 总则

- 不用代码量、界面复杂度、是否由 AI 辅助创作或作者知名度判断质量。
- 小功能只要真实、好用且有明确价值，就可以通过。例如只在输入框上增加输入锁的脚本，虽然实现简单，但能解决具体问题，也值得上架。
- AI 生成不是拒绝理由；**明显幻觉、虚构功能或不可用内容**才是问题。
- 已通过作者的历史记录可以降低常规更新的审核成本，但不能掩盖恶意破坏或新增风险。
- 命令拼接、Shell 调用、高权限调用、后台进程或较宽的文件访问范围，本身属于小风险，不单独作为要求修改或拒绝的理由。它们在功能需要且行为可理解时可以通过。
- 插件在用户可见的配置界面中提供由用户自行填写的 Endpoint/URL（以及相应的 API Key）时，向该地址发送实现该功能所需的数据，视为用户已知并主动选择的上传行为；市场说明未逐项重复该联网行为，不单独作为要求修改的理由。仍须审查隐藏的默认地址、未由该配置指向的外传，以及与该功能无关的数据发送。
- 只有存在明确的恶意行为、隐蔽的数据外传、无关的破坏性操作、后门，或风险明显超出功能需要时，才以安全问题拦截。

## 审核方式

### 0. 自动审核的确定性元数据修正

Codex 等自动审核器可以代替作者完成**可由实际发行内容确定的元数据修正**，但必须先核对待审版本、最近已通过版本和实际包或仓库差异，并通过带管理员或审核员令牌的 `POST /market/v2/entries/{entryId}/review/metadata` 接口写入待审版本；不得直接操作数据库。

- 作者未填写更新说明时，只要审核器能可靠地确定相对基线版本的真实改动，就应使用 `detailAppend` 将简明、事实性的更新说明追加到待审版本的 `entryPatch.detail`。说明至少写明对比基线、具体功能或行为变化，以及新增的联网、权限、数据处理或安全影响；保留作者原有说明，不得根据不完整证据臆测作者意图。
- 待审 artifact 包中出现 `ToolPkg._m(...)` 时，审核器应将该待审版本的 `minAppVer` 自动更正为不低于 `1.12.0+9`。这是兼容性元数据修正，不要求作者重新打包或重新投稿。
- 上述修正只能作用于 `pending` 版本，完成后仍须走普通 `approve` 审核；在通过前不得改变公开市场页。无法可靠建立差异、说明会包含推测，或内容本身仍有风险时，才使用 `changes` 和 `metadata-incomplete` 要求作者补充。

### 1. 原作者的后续版本

同一项目、同一作者，且此前已有通过版本时，默认快速通过。

只要没有明显的恶意破坏、投毒、隐私侵害、无关内容替换或其他新增高风险行为，就可以通过。常规的功能增加、修复、重构、文案调整和小范围体验优化，无需因为功能小或改动不大而卡住。Shell、高权限调用或命令拼接等实现风险，若服务于声明功能且未发现恶意用途，也按可通过处理。

出现异常信号时再深入查看，例如把原有功能替换为空壳或广告、突然加入无关的联网/命令执行、明显破坏原有能力，或存在故意规避审核的迹象。

### 2. 其他作者提交已有项目的新版本

当最近已通过版本是原作者发布，而待审版本由其他作者提交时，必须把仓库拉下来，与最近已通过版本对比。

投稿者必须在 `changelog` 或随该版本提交的条目详情中写清楚相对最近已通过版本的改动，至少包括：对比基线版本、具体修改的功能或文件、行为变化，以及新增联网、权限、数据处理或安全影响。第三方投稿者可在新版本的 `entry` patch 中更新 `description` 和 `detail`；这两项在审核通过前不会改变公开市场页，标题、分类和公开更新策略仍只允许原作者修改。`修复问题`、`优化`、`修改版` 等笼统表述不能代替变更说明。缺少这份说明时，优先按“自动审核的确定性元数据修正”补充；只有审核器无法可靠写出事实性摘要时，才以 `changes` 和 `metadata-incomplete` 要求作者补充。

人工需判断三件事：

1. 投稿说明是否准确、完整地对应实际差异；
2. 改动是否有实际意义，例如修复缺陷、改善兼容性、补齐功能或优化体验；
3. 改动带来的风险是否很小或没有明显恶意风险。

三项均满足即可通过。第三方修复版可以通过，不因提交者不是原作者而额外设限。

重点排除无意义或幻觉式改动：声称修复但没有对应实现、调用不存在的 API 或文件、只堆砌自动生成内容、用占位符冒充功能，或借小改动夹带无关的危险行为。

### 3. 首次发布

首次发布主要看三点：风险、真实性和质量。

- **风险：** 是否有明确的不合理数据外传、破坏性操作、隐蔽恶意执行或其他会伤害用户的行为。正常功能所需的 Shell、高权限、后台进程或文件访问可接受。
- **真实性：** 描述的功能是否在内容中真实存在；不要接受虚构 API、虚构能力、空壳实现或明显无法工作的内容。
- **质量：** 是否解决了明确问题，用户是否能从中获得实际价值。功能可以简单，不要求大而全。

对首次发布不要求追求复杂设计或“看上去高级”。一个边界清楚、行为可靠的小工具，通常比功能描述很大但充满幻觉的项目更应该通过。

## 结论

### 通过

改动有意义，内容真实，风险小或没有风险时通过。

### 要求修改

内容本身可能有价值，但存在明显幻觉、描述与实现不符或需要作者补正的问题时，要求修改后重新提交。

市场简介仅重复标题、市场登记版本与发行内容版本不一致，或第三方更新缺少可核验的变更说明且审核器无法基于可靠差异补充事实性摘要时，均属于必须要求修改的情形。

### 拒绝

内容不可用、明显虚构、风险不可接受、恶意破坏、重复灌水或违反平台规则时拒绝。

审核意见只写实际发现的问题即可，不用重复记录审核路径或一般系统校验结果；这些信息由系统留存。版本登记不一致及第三方更新说明缺失是例外，必须在 `reviewDetail` 写明。对打回和拒绝，请通过 `reviewDetail` 给作者留下足以修正或理解结论的具体说明。

本规范优先保障用户安全和市场内容真实性，同时为真实、有用的创作保留尽可能低的审核阻力。
