# Provider capability mapping

Thinking parameters are now generated by rules in the current model config, and the provider name is no longer treated as a runtime-global capability set:

- When creating a config or switching providers, the collection directory filters out the rules for the corresponding provider and writes them into the model config
- Rules written into the model config match models using the model prefix, inclusion items, regex, first-segment, and last-segment features in `match`
- Each rule declares `control`, `parameterLabel`, `enable`, `disable`, and `options`; the settings page maintains the current config's rules via a dialog form
- OpenRouter/Nous default examples write `reasoning.max_tokens`
- OpenCode default examples identify Google, Anthropic, OpenAI/xAI, and GLM families by the first segment of the model path
- Gemini 2.5 default examples use `thinkingBudget`, while other Gemini examples use `thinkingLevel`
- Older Anthropic models use budgets, newer models use adaptive thinking and effort
- DeepSeek default examples use three `reasoning_effort` tiers: `low`, `high`, and `max`
- Zhipu, Kimi, MiMo, Doubao, SiliconFlow, NVIDIA, and local template capabilities are all expressed through the same rule set
- When an option id is invalid, the request fails, avoiding silently changing the user's selection

Local llama.cpp passes enableThinking into the enable_thinking input field of the llama.cpp chat template.
