# Issue 767 Avatar Config Persistence Fix

## Original State

`avatar_configs` in `avatar_preferences.xml` was deserialized directly by Gson into a non-null domain model. Gson can bypass the Kotlin constructor, so a `data: null` in a persisted record would enter `AvatarConfig`, then trigger a null pointer when reading the avatar path and cause a restart loop.

## Intent of the Fix

- Use a nullable transport model at the persistence read boundary to validate required fields
- Reject corrupted records, ensuring the business layer only receives `AvatarConfig` instances satisfying non-null constraints
- Continue using the existing disk scan to recover avatars, and permanently remove corrupted records through the existing write-back flow
- Add regression tests covering both normal records and `data: null` records

## Scope

Modify the avatar config SharedPreferences decoding flow and its unit tests. The Room database, raw snapshot format, avatar domain interfaces, and user interface are unchanged.

## Expected Results

After restoring data containing a corrupted avatar config, the app can start normally. Valid avatar configs are kept, avatars corresponding to corrupted records are regenerated by disk scanning when the model files exist, and the cleaned-up config is then written back to SharedPreferences.

## Completion Status

- The persistence array is now decoded and validated entry by entry; invalid records do not enter the domain model
- The array position of a corrupted record is written to the app log, and the cleanup result is saved over it after the existing avatar scan finishes
- Regression tests cover `data: null`, missing `data`, wrong data types, and valid record round-trips
